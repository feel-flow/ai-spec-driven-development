# ワークフロー運用原則

> **Parent**: [DEPLOYMENT.md](../DEPLOYMENT.md) | **Related**: [git-workflow.md](./git-workflow.md)

## 概要

AI駆動Git Workflowを効率的に運用するための基本原則を定義します。これらの原則はワークフロー全体に適用され、不要な中断を排除し、スコープの肥大化を防ぎます。

---

## 3つの運用原則

### 原則1: ノンストップフロー

**ルール**: Issue作成からPR作成まで、不要な確認を挟まず一気通貫で進める

```
Issue作成 → ブランチ作成 → 実装 → テスト → セルフレビュー → PR作成
                    ↑ この一連の流れを中断しない ↑
```

**やること**:

- 各ステップを順序通りに連続実行
- セルフレビューの指摘は即座に修正してコミット
- レビュー対応ポリシーに従い、Critical/Warning は確認不要で即対応

**やらないこと**:

- 途中で不要な「これでいいですか？」確認を挟む
- 実装完了後にPR作成を後回しにする
- セルフレビュー結果を報告して承認を待つ

---

### 原則2: スコープ外発見の4段判定

**ルール**: 作業中にスコープ外の改善点・バグを見つけた場合、起票する前に **YAGNI → 同 PR でインライン修正 → 既存の open `bundle` へ追記 → `bundle` 単位で新規起票** の順で判定する。一律に Issue 化せず、一律に「ついで対応」もしない。

| 判定                        | 条件                                                                                                                                       | 対応                                                                                                        |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| YAGNI                       | 現在の根拠（再現例・利用者影響・運用上の痛み・レビュー根拠）も、検証できる受け入れ条件も示せない                                           | 修正せず Issue も作らない。理由を 1 行だけ報告する                                                          |
| 同 PR でインライン修正      | 必要性があり、仕様判断・別モジュール波及・独立した受け入れ条件や検証・変更 10 行超（テスト・fixture は数えない）のどれにも明確に該当しない | 現 PR の fix commit に束ねる                                                                                |
| 既存の open `bundle` へ追記 | 上の 4 条件のどれかに該当し、同じテーマの open `bundle` がある                                                                             | チェックリスト 1 行をコメントで追記する                                                                     |
| `bundle` 単位で新規起票     | 上の 4 条件のどれかに該当し、統合先が無い                                                                                                  | 同じ PR から出た同テーマの発見を 1 つの `bundle` にまとめて起票する（カテゴリ Epic があればその sub-issue） |

`bundle` ラベルが無いリポジトリでは、3・4 段目の「`bundle`」をテーマの合うカテゴリ Epic と読み替え、追記はその Epic へのコメント、起票はその sub-issue として行う。ラベル一覧や Issue 検索が失敗した（非 0 終了・認証エラーなど）ときは「候補なし」とみなさず、起票を止めて原因を報告する。

迷ったときは、必要性を説明できなければ YAGNI、仕様判断の要否と別モジュールへの波及に確信が持てなければ Issue 側、それ以外（規模・局所性・検証の重さ）の迷いはインライン側へ倒す。セキュリティ・データ損失・法令違反の合理的なリスクは「現在の根拠」に含む。

現在の diff が導入・悪化させた回帰、現 Issue の受け入れ条件、既存契約、必須品質ゲート、Critical / Warning の解消はスコープ外ではない。後続 Issue へ送らず、マージ前に現 PR で解消する。

**やること**:

- 最初に現在の根拠と受け入れ条件を確認し、YAGNI なら backlog に積まない
- 必要かつ軽微な発見は、理由を 1 行報告して現 PR で修正する
- 非軽微な発見は、新規作成より先に同じテーマの open `bundle` を検索する
- 起票するときは発見の経緯と受け入れ条件を簡潔に記載する
- 現在のタスクに集中し続ける

**やらないこと**:

- 将来の可能性だけで Issue を作る
- 統合先を探さずに親無しの単独 Issue を作る
- 仕様判断や別モジュール変更を「軽微」として現 PR に混ぜる
- 現 diff の回帰や必須品質ゲートを「別 Issue」として先送りする

**例**:

```bash
# 必要性があり、独立した設計・検証が必要なリファクタリングを発見した場合
repo="OWNER/REPO"
# 0. bundle ラベルの実在を先に確かめる（無いリポジトリでは --label bundle の検索は常に空になり、起票も失敗する）
gh label list --repo "$repo" --search bundle --json name
# 1. 統合先の open bundle を探す（--limit を付けないと 30 件で打ち切られる）
gh issue list --repo "$repo" --state open --label bundle --limit 200 --json number,title,url

# 2a. 同じテーマの bundle があればコメントで追記する
gh issue comment <bundle番号> --repo "$repo" \
  --body "- [ ] UserService.createUser() のメソッド分割（発見元: Issue #123）"

# 2b. 統合先が無いときだけ bundle として起票する
#     bundle ラベルが無いリポジトリでは --label "bundle" を外し、テーマの合うカテゴリ Epic の sub-issue として紐付ける
gh issue create \
  --repo "$repo" \
  --title "refactor: UserService のメソッド分割" \
  --body "## 発見の経緯
Issue #123 の作業中に発見。UserService.createUser() が150行を超えており、
バリデーション・永続化・通知の責務が混在している。

## 提案
- バリデーション、永続化、通知を個別メソッドに分離
- 単体テストの追加

## 優先度
低（機能的には正常に動作中）" \
  --label "refactoring" --label "bundle"
```

### 原則3: 曖昧仕様の確認タイミング

**ルール**: 要件が不明確な場合はIssue着手前にユーザーに確認する。作業開始後に出てきた疑問は原則2の4段判定で扱い、現在の作業を止めない

| タイミング                   | 対応                                       |
| ---------------------------- | ------------------------------------------ |
| Issue着手前                  | 曖昧な要件・仕様をユーザーに確認           |
| 作業開始後（軽微な疑問）     | 原則2の4段判定で扱う。現在の作業は止めない |
| 作業開始後（致命的な不明点） | 例外的に作業を止めてユーザーに確認してよい |

**致命的な不明点の判断基準**:

- 確認しないと実装が物理的に進められない
- 誤った実装をすると大幅な手戻りが発生する
- セキュリティやデータ整合性に直結する

## タスク管理: TodoWrite

ワークフローの各ステップを TodoWrite で管理し、進捗を可視化します。

### 標準チェックリストテンプレート

ワークフロー開始時に以下のタスクリストを作成：

```
1. [ ] Issue: GitHub Issue 作成
2. [ ] Branch: feature ブランチ作成
3. [ ] Implement: 実装・コミット
4. [ ] Test: テスト実行・合格確認
5. [ ] Self-Review: PR Review Toolkit + Codex CLI クロスモデルレビュー
6. [ ] PR: Push + Pull Request 作成
7. [ ] Review: レビュー指摘修正・コミット（修正ループ。人間レビュー時はレビュワーへのサマリーコメント）
8. [ ] Merge: Squash merge
9. [ ] Cleanup: develop 復帰 + `git fetch --prune` + ブランチ削除
10. [ ] ACE: `/ace-curate <PR番号>` でナレッジ体系化
```

### 運用ルール

- タスク開始時に `in_progress` に更新
- タスク完了時に即座に `completed` に更新
- **同時に `in_progress` のタスクは1つだけ**
- スコープ外の発見は新規タスクとして追加せず、原則2の4段判定でルーティング

---

## 原則の適用タイミング

| ワークフローステップ | 適用される原則                                                |
| -------------------- | ------------------------------------------------------------- |
| Issue作成            | 原則3（曖昧仕様の確認）                                       |
| ブランチ作成〜PR作成 | 原則1（ノンストップフロー）                                   |
| 実装中の発見         | 原則2（YAGNI / インライン / bundle 追記 / bundle 起票）       |
| セルフレビュー       | 原則1 + [Review Response Policy](./review-response-policy.md) |
| レビュー対応         | 原則1 + 原則2                                                 |
