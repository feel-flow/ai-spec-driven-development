# SBOM（ソフトウェア部品表）の生成・保存・利用

> **Parent**: [DEPLOYMENT.md](../DEPLOYMENT.md)

本ドキュメントは、SBOM を **依存関係から自動生成する成果物** として扱うための運用手順を定める。SBOM 本体は人が編集する設計書ではない。人が読み、合意して更新するのは本書（生成方法・対象範囲・保存・利用手順）であり、部品表そのものを手で書き換えない。

---

## 1. 目的と限界

SBOM は、リリースに含まれる部品（ライブラリ名・バージョン・識別子）を後から調べるための記録である。主な使い道は次の 2 つ。

- **脆弱性発覚時の影響調査の入力**: 公表された部品とバージョンが、どのリリースに含まれていたかを探す。
- **構成の説明**: 顧客・監査・社内からの「このリリースは何でできているか」に答える。

SBOM は次のものでは **ない**。

| 誤解               | 実際                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------ |
| 脆弱性スキャン     | 部品の一覧であり、脆弱性の有無は別のスキャナ・アドバイザリと照合して判断する                                 |
| 修正・自動更新     | 影響を見つけた後の修正・再配備は通常の変更手順で行う                                                         |
| 安全性の保証       | 生成できたことは、部品が安全であることも、記載部品がすべて実際に使われていることも意味しない                 |
| 配備済み構成の証明 | lockfile などから生成した SBOM は宣言上の構成である。配備との一致はデプロイ記録の SHA と照合して別途確認する |
| 秘密情報の一覧     | 認証情報・キーの管理台帳とは目的も管理対象も異なる。SBOM の生成入力に環境ファイルや認証情報を含めない        |

影響調査では、SBOM で候補部品を見つけた後に、実際の利用箇所・到達可能性・配備状況を調べてから対応を決める。

## 2. 採用判断

ASDD 2.0 の合意方式に従い、すべてのプロジェクトへ一律の必須ゲートとしては追加しない。段階・公開範囲に応じて次を初期推奨とし、採用するかどうかを合意して記録する。

| 段階・状況                                         | 初期推奨                                   |
| -------------------------------------------------- | ------------------------------------------ |
| 試作・PoC（内部利用のみ）                          | 任意。採用しない場合も理由は不要           |
| 継続運用、外部公開、顧客へ納品するソフトウェア     | 推奨候補。採用・見送りと理由を記録する     |
| 厳格運用、契約・規制で部品表の提出を求められる場合 | 要求元の形式・粒度に合わせて採用を検討する |

「標準」の構成を選んだだけで SBOM の生成を有効にしない。採用した場合は、本書 §3〜§6 の項目を `DEPLOYMENT.md`（または `.asdd/config.json` で合意した記録先）へ決定として残す。

## 3. 生成方法の決定

### 形式（CycloneDX / SPDX）

どちらも標準化された SBOM 形式であり、優劣ではなく用途で選ぶ。仕様の版は採用時に公式サイトで確認し、記憶だけで「最新」と記載しない。

| 観点           | 確認すること                                                         |
| -------------- | -------------------------------------------------------------------- |
| 提出先の要求   | 顧客・監査・規制が形式や版を指定していないか                         |
| 利用するツール | 生成ツール・脆弱性照合ツールがどちらの形式・版を読み書きできるか     |
| 記録したい情報 | 依存関係・ライセンス・ビルド情報など、必要な項目を形式が表現できるか |

指定がなく、主用途が依存部品の影響調査であれば、使う照合ツールが読める形式を 1 つ選び、併用はしない。

### 生成ツールと入力

- 生成は **依存定義（manifest・lockfile）やビルド成果物から機械的に行う**。部品表を手で編集しない。
- 生成ツールの版を固定する（自動更新で出力が変わるのを避けるため）。導入時は公式配布物のチェックサムを照合する。
- 入力ファイルを明示的に限定する。リポジトリ全体を走査させると、環境ファイル・認証情報・個人データ・`node_modules` などが入力に混ざる恐れがある。
- 外部サービスへ構成情報を送信する機能（ライセンス照会・更新確認など）は、必要性を合意したときだけ有効にする。

### 対象範囲の明記

生成した SBOM が何を表しているかを、本書の採用記録と生成物の metadata の両方に書く。

| 確認事項       | 例                                                          |
| -------------- | ----------------------------------------------------------- |
| 入力           | lockfile と manifest のみ / コンテナイメージ / ビルド成果物 |
| 含む依存       | 本番依存のみか、開発用・optional・推移依存を含むか          |
| 表しているもの | 宣言上の構成か、配信・実行される成果物の実測か              |
| 含まないもの   | 実行基盤・OS パッケージ・外部 SaaS など                     |

lockfile 由来の SBOM は、開発用依存や対象 OS にインストールされない optional 依存を含みうる。逆に、実行基盤が提供する部品は含まない。

## 4. リリースとの対応（SHA・識別子）

SBOM は「どのコミット・どのリリースのものか」が分からなければ影響調査に使えない。生成物と一緒に、次を記録した metadata を保存する。

| 項目                | 内容                                                                               |
| ------------------- | ---------------------------------------------------------------------------------- |
| コミット SHA        | 生成に使ったコミット。リリースタグ・バージョン番号があれば併記する                 |
| 入力の一致          | 入力ファイルがそのコミットと一致するか。未コミット変更があれば一致しないと明記する |
| 入力・出力の SHA256 | 入力ファイルと SBOM ファイルのハッシュ。取得後の改変・取り違えを検出する           |
| 生成日時・ツール版  | 同じ SHA でも日時やツール版で出力のバイト列は変わりうる                            |
| 部品数・対象範囲    | §3 の対象範囲の要約                                                                |

注意点:

- 確定版の記録は、入力をコミットしてから生成する。作業ツリーから生成したものは確定版と区別できる名前にする。
- CI の PR 実行では、PR head ではなく検証用の merge commit が対象になる場合がある。リリース記録には、リリース対象ブランチの対象 SHA で生成したものを使う。
- 依存定義の変更時だけ自動生成する設定では、すべての配備に対応する SBOM が自動で残るわけではない。リリース対象 SHA での生成をリリース手順に含める。
- 失敗した実行では、過去の出力を新しい成功の証拠として扱わない。

## 5. 保存先・保存期間・閲覧範囲

| 決めること | 判断基準                                                                                                                           |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 保存先     | 短期は CI の artifact でよい。期限を超えて残すリリースは、期限前に取得してアクセス制限付きの保管先へ SBOM と metadata を一緒に移す |
| 保存期間   | 固定値は定めない。リリースのサポート期間（脆弱性対応を続ける期間）＋契約・規制が求める期間を基準に決める                           |
| 閲覧範囲   | リポジトリと同等以上に限定する。部品構成は攻撃の手がかりにもなるため、公開サイトには置かない                                       |
| 担当       | 長期保管先への移動・期限切れ前の取得を誰が行うか                                                                                   |

- SBOM 本体と metadata はリポジトリにコミットしない（生成物の出力先は `.gitignore` に入れる）。保存先は上表で決めた場所とする。
- 方法論・テンプレートのリポジトリには、利用先の SBOM 本体や秘密の値を置かない。

## 6. 生成・保存・取得の手順

### CI を使える環境

1. 生成ジョブを、依存定義・生成処理の変更時と手動実行で動かす。アプリ依存のインストールやビルドが不要な生成方式なら、ジョブを軽く保つ。
2. artifact 名にコミット SHA を含め、保存期間を設定する。
3. リリース時は対象 SHA で手動実行し、artifact を取得して長期保管先へ移す。

### CI を使えない環境

1. 固定した版の生成ツールをローカルに導入し、入力をコミットした状態で生成する。
2. SBOM と metadata を §5 の保管先へ保存する。
3. 記録には **ローカル生成** と書く。CI による自動実行済みとは記録しない。

### 記録の区別

生成しただけでは保存・取得ができたことにならない。次を別々に記録する。

| 記録             | 意味                                                           |
| ---------------- | -------------------------------------------------------------- |
| ローカル生成成功 | 手元で生成できた。保存先への格納は別                           |
| CI 生成成功      | ジョブが成功した。artifact が取得できることは別                |
| 取得・照合成功   | 保存先から取得し、metadata の SHA・ハッシュを照合できた        |
| 長期保管完了     | 期限のない（または合意期間の）保管先へ移し、閲覧範囲を確認した |

### 取得後の確認

1. metadata のコミット SHA と、調査したいリリースのコミットを照合する。
2. 入力がコミットと一致していること、SBOM ファイルの SHA256 が metadata と一致することを確認する。
3. 部品名・バージョン・識別子（purl など）で対象部品を探す。
4. 配備との対応はデプロイ記録の SHA でも確認し、部品表だけで「配信済み」と判断しない。

## 7. 先行試行の参照

FEEL-FLOW のサイト（非公開リポジトリ）で先行試行した。詳細は [Issue #540 のコメント](https://github.com/feel-flow/ai-spec-driven-development/issues/540) を参照する。要約（確認日: 2026-10-07）:

| 区分     | 内容                                                                                                                                                    |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 実測済み | 版を固定した Syft（1.54.1、試行時に固定した版であり推奨版ではない）で、manifest と lockfile の 2 ファイルだけを入力に CycloneDX JSON を生成した         |
| 実測済み | 開発用・optional・推移依存を含む宣言上の構成として 925 部品を記録した                                                                                   |
| 実測済み | metadata にコミット SHA・入力一致・入力/出力 SHA256・生成日時・ツール版・部品数を記録し、CI artifact（SHA 付きの名前、90 日保存）を取得して再照合できた |
| 実測済み | CI の PR 実行では検証用 merge commit の SHA が対象になった                                                                                              |
| 制約     | 依存定義の変更時だけ自動生成するため、全配備の SBOM は自動では残らない。リリース対象 SHA は手動実行を併用する                                           |
| 未確認   | 90 日を超える長期保管先への移動、配信物そのものの実測、本番リリースでの運用                                                                             |
