# 外部連携のキー一覧（運用管理文書）

> **Parent**: [DEPLOYMENT.md](../DEPLOYMENT.md)

本ドキュメントは、外部サービスとの連携に使う認証情報・識別子の **一覧（キー一覧）** を、**人が運用事実を確認して書く管理文書** として扱うためのテンプレートと運用ルールを定める。一覧は秘密の値の保管庫ではない。秘密の値は既存のシークレット管理基盤（CI の secrets、ホスティングの環境変数、パスワードマネージャなど）に保管し、一覧にも本書にも記録しない。

本書（テンプレートとルール）は公開物である。各プロジェクトの **実際の一覧** はアクセスを制限したプロジェクト文書に置く（§7）。

---

## 1. 目的と限界

キー一覧は、漏えい・失効・権限変更・担当変更が起きたときに「どのキーが、何のために、どの環境で使われ、誰が、どこで管理しているか」を即座に答えるための記録である。主な使い道は次の 3 つ。

- **事故時の影響範囲の特定**: 漏えいした可能性のあるキーの用途・環境・権限から、止める範囲と再発行の順序を決める。
- **失効・更新の見落とし防止**: 有効期限・担当・最終確認日を見て、放置されているキーを見つける。
- **引き継ぎ**: 担当が変わっても、どこを確認すればよいかが分かる。

キー一覧は次のものでは **ない**。

| 誤解                 | 実際                                                                                                                 |
| -------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 秘密の値の保管庫     | 値は書かない。書くのは保管先の **参照**（保管庫の名前・設定名）だけ。値を書いた一覧は漏えい源になる                  |
| 権限縮小・失効の記録 | 一覧を作っただけでは、権限縮小・失効・更新は実施されていない。実施は別の作業であり、実施した事実と日付を別に記録する |
| 自動生成物           | コードから設定名は読めるが、実際の発行単位・権限・保管状況・担当は管理画面や管理者に確認しなければ分からない         |
| SBOM                 | SBOM は依存部品の一覧を機械生成する成果物。キー一覧は運用事実を人が確認する管理文書（§8）                            |
| 監査の完了証明       | 最終確認日は「その日に事実を確認した」記録であり、確認した内容が正しい状態であることの保証ではない                   |

## 2. 採用判断

ASDD 2.0 の合意方式に従い、すべてのプロジェクトへ一律の必須ゲートとしては追加しない。外部連携の数と影響に応じて次を初期推奨とし、採用するかどうかを合意して記録する。

| 段階・状況                                                 | 初期推奨                                                     |
| ---------------------------------------------------------- | ------------------------------------------------------------ |
| 試作・PoC（外部連携が無い、または使い捨ての試用キーのみ）  | 任意。採用しない場合も理由は不要                             |
| 継続運用、本番環境で外部サービスの認証情報を使う           | 推奨候補。採用・見送りと理由を記録する                       |
| 顧客データ・決済・個人情報に触れる連携、契約で管理を求める | 採用を強く推奨。確認頻度と担当を §6 に従って決め、記録を残す |

「標準」の構成を選んだだけでキー一覧を必須にしない。採用した場合は、本書 §3〜§7 の決定を `DEPLOYMENT.md`（`.asdd/config.json` の文書構成で運用観点を別の文書に配置している場合はその文書）へ決定として残し、実際の一覧は §7 で決めた保存先に置く。

## 3. 記録項目とテンプレート

### 記録項目

| 項目               | 記録する内容                                                                                                               |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| サービス           | 連携先のサービス名                                                                                                         |
| 用途               | 何のために使うか（例: エラー収集、メール送信、決済）                                                                       |
| 対象環境           | production / staging / 開発者ローカルなど。環境ごとに行を分ける                                                            |
| 専用・共用         | このプロジェクト専用に発行したキーか、他プロジェクト・他チームと共用しているか                                             |
| 権限範囲           | 読み取りのみ / 書き込み / 管理者など。公開用識別子なら「該当なし（公開識別子）」                                           |
| 保管先の参照       | 保管庫の名前と設定名（例: CI secrets の `MAIL_API_KEY`）。**値ではない**。「確認先」と「確認済みの保管先」を区別する（§5） |
| 管理担当           | 発行・更新・失効を行える人または役割。個人名を公開文書に書かない                                                           |
| 最終確認日         | 管理画面・管理者で事実を確認した日。**文書を編集した日を確認日にしない**                                                   |
| 更新・失効時の対応 | ローテーション・失効のときに必要な作業（再配備、設定の差し替え、依存する連携への連絡など）                                 |
| 確認状態           | 確認済み / 未確認。未確認は `未確認（確認担当: ○○ / 次の手順: ○○）` と書く（§5）                                           |

行は **環境別・資格情報別** に分ける。1 つのサービスでも、本番用の秘密キーと公開用識別子は別の行にする。

### テンプレート

次の表をコピーして使う。秘密の値を書く列は **意図的に設けていない**。列を追加するときも、値を書く列は作らない。

```markdown
| サービス | 用途 | 対象環境 | 専用・共用 | 権限範囲 | 保管先の参照 | 管理担当 | 最終確認日 | 更新・失効時の対応 | 確認状態 |
| -------- | ---- | -------- | ---------- | -------- | ------------ | -------- | ---------- | ------------------ | -------- |
|          |      |          |            |          |              |          |            |                    |          |
```

### 記入例

架空のサービスによる例。実在の組織・実値・内部の保管先は書かない。

| サービス        | 用途           | 対象環境   | 専用・共用 | 権限範囲               | 保管先の参照                            | 管理担当         | 最終確認日 | 更新・失効時の対応                                               | 確認状態                                                                        |
| --------------- | -------------- | ---------- | ---------- | ---------------------- | --------------------------------------- | ---------------- | ---------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Example Mailer  | 通知メール送信 | production | 専用       | 送信のみ               | ホスティングの環境変数 `MAILER_API_KEY` | 運用担当（役割） | YYYY-MM-DD | 再発行後に環境変数を差し替えて再配備。旧キーは配備確認後に失効   | 確認済み                                                                        |
| Example Metrics | 利用状況の計測 | production | 共用       | 該当なし（公開識別子） | ソース内の設定（公開値。保管庫は不要）  | 未確認           | —          | ローテーション不要。計測先を変えるときはソースの設定値を更新する | 未確認（確認担当: サービス管理者 / 次の手順: 管理画面で発行単位と共用先を確認） |

## 4. 秘密の認証情報と公開用識別子

同じ「キー」と呼ばれていても、漏えいしたときの影響と必要な運用は異なる。混同すると、存在しない権限の縮小や不要なローテーションを公開識別子へ要求したり、逆に秘密の値を公開値と同じ扱いで置いたりする。

| 区分           | 例                                                                                            | 一覧での扱い                                                                                                                   |
| -------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 秘密の認証情報 | API のシークレットキー、サービス用トークン、管理用トークン、署名用シークレット、DB 接続文字列 | 権限範囲・保管先の参照・ローテーション時の対応を必ず記録する。値はどこにも書かない                                             |
| 公開用識別子   | publishable key、client ID、計測 ID、サイト識別子、エラー収集の送信先識別子（DSN 等）         | 権限範囲は「該当なし（公開識別子）」。ローテーションや権限縮小を要求しない。どこに埋め込まれているか（ソース・設定）を記録する |

注意点:

- 公開用識別子でも、**同じサービスの管理用トークン** は秘密の認証情報として別の行にする（例: エラー収集サービスの送信先識別子は公開値、同サービスの管理 API トークンは秘密）。
- 区分が分からないキーは、分かるまで秘密として扱い、確認状態に「区分未確認」と書く。サービスの公式文書で公開可とされていることを確認してから公開用識別子に移す。
- 公開用識別子であっても、サービスの設定（送信元ドメインの制限、許可オリジンなど）が無効だと悪用されうる。制限の有無は「管理画面で確認する事実」として扱う（§5）。

## 5. コードから読める事実と確認が必要な事実

一覧の品質は、**何を根拠に書いたか** で決まる。コードや設定ファイルを読めば分かることと、管理画面・管理者に確認しなければ分からないことを分け、後者を推測で埋めない。

| 根拠                   | 分かること                                                                     | 分からないこと（確認が必要）                                                                 |
| ---------------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| コード・設定ファイル   | 設定名（環境変数名）、読み込み箇所、使っている SDK・エンドポイント、用途の推定 | 実際に発行されたキーの数、権限、有効期限、共用先、誰が発行したか、保管庫に本当に入っているか |
| CI・ホスティングの設定 | secrets・環境変数の **名前** が存在するか                                      | 値が有効か、どのキーの値か、サービス側の権限                                                 |
| サービスの管理画面     | 発行単位、権限、有効期限、最終利用日、制限設定                                 | （これが確認の到達点）                                                                       |
| 管理者への確認         | 管理画面を見られない担当者が、上記を管理者から聞いた事実                       | 聞き取りの日付と相手を記録する。文書の編集日を確認日にしない                                 |

「保管先の参照」では、**確認先**（ここにあるはずだ）と **確認済みの保管先**（ここにあることを確認した）を区別する。確認するまでは確認先であり、確認状態は未確認のままにする。

### 未確認の記録書式

管理画面を見られない担当者が一覧を作る場合でも、未確認を未確認のまま残せば一覧は役に立つ。空欄や推測ではなく、次の書式で **確認担当と次の手順** を残す。

```text
未確認（確認担当: <役割または担当> / 次の手順: <管理画面のどこを見るか、誰に何を聞くか>）
```

例: `未確認（確認担当: サービス管理者 / 次の手順: 管理画面の API キー一覧で発行単位と権限を確認し、最終確認日を記入）`

未確認の行が残っていても、一覧の採用や公開を妨げない。妨げるのは、未確認を確認済みのように書くことである。

## 6. 更新手順と定期確認

### 更新のトリガ

次の出来事と **同時に** 一覧を更新する。後でまとめて更新する運用は、事故時に一覧が古い状態で参照される原因になる。

| トリガ               | 更新する項目                                                 | 一覧とは別に記録すること                                 |
| -------------------- | ------------------------------------------------------------ | -------------------------------------------------------- |
| 新しい連携の導入     | 行を追加（環境別・資格情報別）。保管先の参照と権限範囲を記録 | 発行者と発行日                                           |
| 権限の変更           | 権限範囲、最終確認日                                         | 変更した日と理由                                         |
| ローテーション・失効 | 最終確認日、更新・失効時の対応の見直し                       | 新しい値への差し替えと **再配備・反映の確認** が済んだか |
| 担当の変更           | 管理担当                                                     | 引き継ぎ日。旧担当しか知らない保管先がないか             |
| 連携の廃止           | 行を削除せず、失効済みと日付を記録してから一定期間後に整理   | 失効した日、残存する設定の削除                           |

ローテーション・失効を一覧に書いただけでは完了ではない。再配備・反映の確認は別の作業であり、その実施を別途記録する。

### 定期確認の担当と頻度

固定の頻度を押し付けない。次の観点から担当と頻度を決め、決定を §2 の記録に残す。

| 観点           | 頻度を上げる方向                                                     |
| -------------- | -------------------------------------------------------------------- |
| 連携の数       | 行が多いほど、放置される行が増えやすい                               |
| 影響の大きさ   | 決済・個人情報・本番データに触れる権限を持つキーがある               |
| 共用の有無     | 他プロジェクト・他チームと共用するキーは、自分の知らない変更が起きる |
| 有効期限の有無 | 期限付きキーは、期限より前に確認の機会を置く                         |
| 担当の分散     | 管理画面を見られる人が少ないほど、確認を予定に組み込む必要がある     |

定期確認では、各行の最終確認日と確認状態を更新し、未確認の行の「次の手順」が実行できたかを確認する。確認したが変化が無かった場合も、最終確認日は更新する。

## 7. 保存先と公開範囲

| 決めること         | 判断基準                                                                                                                                  |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 実際の一覧の保存先 | アクセスを制限したプロジェクト文書に置く（非公開リポジトリの `docs/05-operations/` 配下、社内 Wiki など）。**公開リポジトリには置かない** |
| 公開してよいもの   | 本書のようなテンプレートとルールだけ。サービス名の組み合わせ・保管庫の構成・担当の役割も内部の管理情報であり、公開テンプレートに混ぜない  |
| 閲覧範囲           | リポジトリと同等以上に限定する。一覧は攻撃者にとって「どこを狙えばよいか」の地図になる                                                    |
| 値の保管先         | 既存のシークレット管理基盤。一覧の「保管先の参照」はその基盤を指す参照であり、一覧が基盤の代わりにならない                                |
| 形式               | 連携の数と更新頻度が小さいうちは Markdown の表で十分。管理画面やデータベースの自作を初期要件にしない                                      |

### 管理画面を自作しない判断基準

次のすべてに当てはまる間は、Markdown の表（§3 のテンプレート）で運用する。

- 行数が、1 画面で見渡せる範囲に収まる
- 更新が、§6 のトリガが起きたときと定期確認のときだけで、日常的に増減しない
- 閲覧・編集できる人が、リポジトリや Wiki の権限で既に制御できている

いずれかを超えたときに初めて、既存のシークレット管理基盤や資産管理ツールの一覧機能で代替できないかを先に検討し、自作は最後の選択肢にする。

## 8. SBOM との対比

SBOM（[sbom.md](sbom.md)）とキー一覧はどちらも「何が含まれているか」の記録だが、作り方と更新の仕方が異なる。

| 観点         | SBOM                                                    | キー一覧                                                   |
| ------------ | ------------------------------------------------------- | ---------------------------------------------------------- |
| 性質         | 依存関係から **機械的に生成する成果物**。手で編集しない | 運用事実を **人が確認して書く管理文書**                    |
| 入力         | manifest・lockfile・ビルド成果物                        | コードの設定名＋管理画面・管理者への確認                   |
| 更新の契機   | 依存定義の変更、リリース                                | 導入・権限変更・失効・担当変更、定期確認                   |
| 正しさの担保 | 入力と生成手順                                          | 根拠（§5）と最終確認日、未確認の明示                       |
| 置き場所     | リポジトリにコミットしない。アクセス制限付きの保管先    | 公開リポジトリに置かない。アクセス制限したプロジェクト文書 |

共通点は、どちらも秘密の値の保管庫ではないこと、そして生成・作成できたこと自体を安全性の証拠にしないことである。

## 9. 先行試行の参照

非公開のサイトリポジトリで、テンプレートに先立って実際の一覧を作る試行を行った。経緯は [Issue #541 のコメント](https://github.com/feel-flow/ai-spec-driven-development/issues/541) を参照する。本書に反映した要点:

- 実装上の設定名と、実際の発行・権限・保管状況を分けて記録する（§5）。
- 公開識別子と秘密の管理用トークンを区別し、同じサービスでも行を分ける（§4）。
- 未確認の項目は「要確認」のまま残し、文書を編集した日を確認日にしない（§3・§5）。
- 変更と同時に一覧を更新し、再配備・反映の確認は別に記録する（§6）。

試行先での担当者による実態確認は、本書の執筆時点で未完了である。一覧の器ができたことと、事実の確認が済んだことは区別する。
